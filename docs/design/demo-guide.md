## 🚀 第一部分：项目建设背景与架构总览

针对智能货柜业务设备规模大、IoT交互复杂、AI视觉验证困难等痛点，我们基于“补充设计文档”构建了这套**高保真、数据驱动**的质量基础设施。

### 核心技术栈映射

当前平台工程已完美落实了补充设计中的技术选型：

- **底座基建 (Docker)**：MySQL (业务元数据) + Redis (调度缓存) + Kafka (消息与流控) + ClickHouse (度量指标 OLAP) + Elasticsearch (全链路 Trace)。
- **核心大脑 (FastAPI)**：通过 Python 快速构建了并发极佳的后台调度与逻辑引擎，提供了开箱即用的 REST API，并内嵌了多租户和环境隔离的底层逻辑。
- **用户门户 (React+Vite)**：基于 Ant Design 组件库，打造了深色侧边栏+高亮内容区的现代化测试工作台。

## 🖥️ 第二部分：前端 6 大核心模块演示指南

您可以打开 `http://localhost:3000` ，结合以下话术逐一演示侧边栏的六大板块：

### 1. 质量大盘 (Dashboard)

- **演示定位**：测试体系的“驾驶舱”，对应架构的 `[平台度量体系]`。
- **讲解要点**：
  - 这里汇总了全大盘最核心的北极星指标：自动化用例通过率（代表稳定性）、活跃告警数（代表风险隐患）、以及发布成功率（代表 CI/CD 拦截有效性）。
  - 通过这个页面，技术 Leader 可以每天早会一秒看懂当前的系统健康状态。

### 2. 设备农场 (Device Farm)

- **演示定位**：IoT 管理中枢，对应架构的 `[设备生命周期管理]` 和 `[IoT仿真保真度分层]`。
- **讲解要点**：
  - 请注意列表中的 `VIRTUAL` 和 `REAL` 标签。这不仅是个名字，它代表我们在后台实现了从 L1(轻量级协议模拟)、L2(状态机流转) 到 L3(真实物理控制) 的多级仿真调度。
  - 通过右上角的注册入口与环境区分（dev/staging），真正做到了测试数据的租户隔离与防污染。

### 3. AI 评测中心 (AI Eval)

- **演示定位**：全链路测试最“硬核”的区域，对应架构的 `[AI评测自动化流水线]`。
- **讲解要点**：
  - 传统的 AI 模型评测是一个割裂的线下过程。现在，我们将其做成了自动化流水线。
  - 演示点击“触发评测流水线”，您可以引导观众看下方的进度条：平台会自动去完成 `拉取基线模型 -> 利用 GPU 集群批量推理 -> 比对 Ground Truth 生成结果`，彻底解放了算法和测试工程师的双手。

### 4. 用例管理 (Test Cases)

- **演示定位**：用例资产化，对应架构的 `[测试用例管理]`。
- **讲解要点**：
  - 我们的测试体系是“金字塔形”的。列表中清楚地标明了用例的 Level 层级（E2E / INTEGRATION / API）和归属模块（IOT / AI / PAYMENT）。
  - 这保证了每次代码合并时，系统能精准抽出对应的用例集进行局部回归，而不是盲目地全量跑，极大缩短了回归耗时。

### 5. 缺陷闭环追踪 (Defects)

- **演示定位**：质量防漏网，对应架构的 `[缺陷闭环流程]`。
- **讲解要点**：
  - 这不仅仅是个 Jira。当底层的自动化用例（如支付超时）失败时，后台会自动拿着 TraceID 来这里创建一个“自动缺陷”。
  - 列表上标红的 P1、P2 严重级别，帮助团队一眼认清优先级，并且提供了直达日志系统的 Trace 追踪入口。

### 6. CI/CD 质量门禁 (Quality Gate)

- **演示定位**：发布防火墙，对应架构的 `[质量门禁设计]`。
- **讲解要点**：
  - 这是每次版本发布的最后一道关卡。像“AI准确率”、“自动化通过率”都是系统自动校验的硬性指标。
  - 如果展示出红色的 `未通过`，版本就会被物理阻断。只有点击下方显眼的 `申请紧急发布豁免`（走双签审批流），才能放行带病上线，从根源上控制了线上事故率。

## 🛠️ 第三部分：后台代码结构如何支撑业务？

为了让平台具备高扩展性，我们在 `backend/app/` 目录中遵循了严格的领域驱动设计：

1. **`models/` (数据字典)**：包含 `user`, `device`, `task`, `quality_gate`, `testcase`, `defect` 六大核心表，严格落地了《补充设计.md》对数据维度的要求。
2. **`api/v1/` (接口调度)**：与前端 6 大模块一一映射，确保了前后端的低耦合。
3. **`services/iot_service.py` (核心引擎)**：内置了 IoT 状态机的流转引擎代码，是智能货柜“虚拟测试”的灵魂所在。
4. **统一中间件**：通过 `docker-compose` 起停，后续无论是扩容 Kafka 集群以应对并发，还是将 ClickHouse 迁移上云，代码层几乎都是 0 改造。
