# 智能货柜全链路测试平台 — 补充设计

> 本文档是对《智能货柜全链路测试平台设计》的补充完善，覆盖可观测性、安全合规、质量门禁、分期落地等关键环节。

---

## 一、可观测性体系设计

### 1.1 三大支柱

```text
┌─────────────────────────────────────────────────────────────┐
│                    可观测性统一平台                            │
├──────────────┬──────────────────┬───────────────────────────┤
│    日志 Logs  │    指标 Metrics  │     链路 Traces           │
├──────────────┼──────────────────┼───────────────────────────┤
│ 设备日志      │ 设备在线率        │ 用户扫码 → 开门 → AI识别   │
│ IoT消息日志   │ 任务队列深度      │ → 订单生成 → 支付扣款       │
│ AI推理日志    │ AI识别成功率      │                           │
│ 业务日志      │ 调度延迟          │ 每步耗时 + 状态 + 异常     │
└──────────────┴──────────────────┴───────────────────────────┘
```

### 1.2 日志采集方案

| 日志类型 | 采集方式 | 存储 | 保留策略 |
|---------|---------|------|---------|
| 设备运行日志 | Agent 上报 → Kafka | Elasticsearch | 热 7 天 / 温 30 天 / 冷归档 |
| IoT 消息日志 | EMQX Hook → Kafka | ClickHouse | 90 天 |
| AI 推理日志 | 推理服务 SDK | ClickHouse | 180 天 |
| 平台操作日志 | 拦截器 | MySQL + ES | 永久 |
| 测试执行日志 | 测试引擎 SDK | Elasticsearch | 180 天 |

### 1.3 监控指标体系

#### 平台自身健康度

```text
核心指标：
├── 调度引擎
│   ├── 任务排队时长（P50 / P99）
│   ├── 任务执行成功率
│   └── 并发任务数
├── 设备农场
│   ├── 设备在线率（按区域 / 国家）
│   ├── 设备占用率
│   └── 设备故障率
├── IoT 仿真引擎
│   ├── 虚拟设备在线数
│   ├── 消息吞吐量（msg/s）
│   └── 连接建立延迟
└── AI 验证中心
    ├── 推理队列深度
    ├── 推理平均耗时
```

#### 业务质量指标

```text
核心指标：
├── AI 识别质量

│   └── 识别延迟

│   ├── 金额准确率
│   └── 支付成功率

│   ├── 摄像头故障率

    ├── 自动化覆盖率
```

### 1.4 告警规则设计

| 告警级别 | 触发条件 | 通知方式 | 响应时效 |
|---------|---------|---------|---------|
| P0 - 致命 | 设备在线率 < 50% / 支付链路全面失败 | 电话 + 短信 + 飞书群 | 5 分钟 |
| P1 - 严重 | AI 准确率骤降 > 5% / 任务成功率 < 80% | 短信 + 飞书群 | 15 分钟 |
| P2 - 警告 | 单设备离线 / 队列积压 > 100 | 飞书群 | 1 小时 |
| P3 - 提示 | 固件版本落后 / 测试覆盖率下降 | 飞书消息 | 当天 |

## 二、数据隔离与环境管理

### 2.1 多租户隔离模型

```text
组织（Organization）
├── 项目（Project）
│   ├── 测试环境（Environment）
│   │   ├── 设备池
│   │   ├── 数据源
│   │   └── Mock 配置
│   ├── 用例库
│   └── 成员与权限
└── 全局资源
    ├── 共享设备池
    ├── AI 模型仓库
    └── 第三方 Mock 服务
```

### 2.2 环境管理策略

| 环境 | 用途 | 数据策略 | 设备策略 |
|------|------|---------|---------|
| dev | 开发自测 | 每日自动重置 | 虚拟设备为主 |
| staging | 集成测试 | 每次发布前重置 | 虚拟 + 少量真机 |
| pre-prod | 预发布验证 | 脱敏的生产数据快照 | 专用真机池 |
| prod | 生产验证 | 只读，不写入 | 专用生产验证设备 |

### 2.3 测试数据生命周期

```text
创建 → 注入 → 执行 → 采集 → 分析 → 归档 → 清理
 │                      │              │
 └── 自动化生成          └── 自动关联    └── 按策略自动清理
     或从数据集导入          TraceID        （默认 30 天）
```

## 三、安全与合规设计

### 3.1 权限模型（RBAC）

| 角色 | 设备控制 | 测试执行 | 数据查看 | 配置管理 | AI 模型管理 |
|------|---------|---------|---------|---------|------------|
| 超级管理员 | 全部 | 全部 | 全部 | 全部 | 全部 |
| 测试负责人 | 申请审批 | 全部 | 全部 | 测试相关 | 只读 |
| QA 工程师 | 申请使用 | 自己的项目 | 自己的项目 | 无 | 无 |
| 开发工程师 | 只读 | 关联项目 | 关联项目 | 无 | 无 |
| 算法工程师 | 无 | AI 相关 | AI 相关 | 无 | 全部 |
| 海外运营 | 无 | 无 | 对应区域 | 运营配置 | 无 |

### 3.2 设备控制安全

```text
远程操作审批流程：
├── 低风险操作（查看状态、查看摄像头）→ 直接执行
├── 中风险操作（重启、固件升级）→ 需 1 人审批
├── 高风险操作（远程开门、批量重启）→ 需 2 人审批
└── 危险操作（恢复出厂、删除设备）→ 需管理员 + 运维双审批
```

### 3.3 支付隔离策略

```text
测试环境支付隔离：
├── 测试专用支付渠道（不走真实银行通道）
├── 固定测试金额（0.01 元）标识
├── 所有测试交易自动标记 + 定时清理
└── 生产验证设备使用独立沙箱账号，资金可追溯
```

### 3.4 海外合规要求

| 地区 | 合规要求 | 平台应对措施 |
|------|---------|-------------|
| 欧洲 | GDPR | 测试数据脱敏、数据不出境、支持数据删除请求 |
| 美国 | CCPA | 用户数据最小化采集、隐私测试场景覆盖 |
| 东南亚 | 各国数据本地化 | 多 Region 部署、数据就近存储 |
| 全球 | PCI-DSS | 支付数据加密、测试环境隔离 |

## 四、质量门禁设计

### 4.1 门禁规则配置

```yaml
# 质量门禁规则示例
quality_gate:
  name: "版本发布门禁"
  rules:
    - name: "AI识别准确率"
      metric: ai_accuracy
      threshold: 0.95
      operator: gte
      scope: "全部SKU"

    - name: "API自动化通过率"
      metric: api_pass_rate
      threshold: 0.98
      operator: gte

    - name: "全链路冒烟通过"
      metric: smoke_pass
      threshold: true
      operator: eq

    - name: "无P0级缺陷"
      metric: p0_bug_count
      threshold: 0
      operator: eq

    - name: "性能基线不退化"
      metric: performance_regression
      threshold: 0.1
      operator: lte  # 退化不超过10%

  action:
    on_pass: auto_approve
    on_fail: block_release
    notify: [qa_lead, tech_lead]
```

### 4.2 CI/CD 集成方式

```text
代码提交
    │
    ▼
CI 流水线（编译 + 单元测试）
    │
    ▼
触发测试平台 API
    │
    ├── API 自动化测试
    ├── IoT 仿真测试
    ├── AI 回归测试
    └── 冒烟测试
    │
    ▼
测试平台回调结果
    │
    ├── 通过 → 自动合并 / 允许发布
    └── 失败 → 阻断 + 通知
```

### 4.3 紧急发布豁免机制

```text
豁免流程：
├── 发起人填写豁免申请（原因 + 风险评估 + 回滚方案）
├── 审批人：技术负责人 + QA 负责人
├── 豁免后自动标记为「带风险发布」
├── 发布后 24 小时内必须补跑回归
└── 豁免记录纳入月度质量报告
```

## 五、缺陷闭环流程

### 5.1 自动化缺陷关联

```text
测试失败
    │
    ▼
自动捕获
├── 失败截图 / 视频
├── TraceID（全链路日志）
├── 环境信息
├── 设备信息
└── AI 识别结果（如适用）
    │
    ▼
自动创建缺陷单
├── 关联测试用例
├── 关联 TraceID
├── 附带环境快照
└── 自动分配（按模块 / Owner）
    │
    ▼
修复后
├── 自动触发关联用例回归
├── 回归通过 → 自动关闭缺陷
└── 回归失败 → 重新打开 + 通知
```

### 5.2 缺陷分析维度

```text
缺陷看板：
├── 按模块分布（IoT / AI / SaaS / 支付 / 设备）
├── 按严重级别趋势
├── 按发现阶段分布（单元 / 集成 / 回归 / 线上）
├── 缺陷密度（每千行代码 / 每百个接口）
├── 缺陷修复时效（MTTR）
└── 缺陷逃逸率（线上发现 / 总缺陷）
```

## 六、测试用例管理

### 6.1 用例分层策略

```text
用例金字塔：
        ┌───────┐
        │ E2E   │  ← 全链路冒烟（50 条）
       ┌┴───────┴┐
       │ 集成测试  │  ← 模块间交互（200 条）
      ┌┴─────────┴┐
      │ 接口测试    │  ← API / IoT 协议（1000 条）
     ┌┴───────────┴┐
     │ 单元测试      │  ← 函数 / 组件（5000 条）
     └──────────────┘

执行策略：
├── 冒烟：每次提交触发
├── 接口：每次合并触发
├── 集成：每日定时触发
└── E2E：版本发布前触发
```

### 6.2 用例与需求追溯

```text
需求（Jira / 飞书）
    │
    ├── 关联测试用例（1:N）
    │   ├── 正向用例
    │   ├── 异常用例
    │   └── 边界用例
    │
    └── 覆盖度看板
        ├── 已覆盖需求占比
        ├── 未覆盖需求清单
        └── 覆盖度趋势
```

### 6.3 用例维护机制

| 维护场景 | 触发条件 | 责任人 | 动作 |
|---------|---------|--------|------|
| 需求变更 | 需求状态变为「已变更」 | 对应 QA | 更新用例 + 通知评审 |
| 用例失败 | 连续 3 次执行失败 | 用例 Owner | 排查是用例问题还是产品缺陷 |
| 定期 Review | 每月 1 次 | QA 负责人 | 清理过时用例 + 补充新场景 |
| 新功能上线 | 功能合并到主分支 | 功能开发者 + QA | 补充用例 + 更新回归集 |

## 七、IoT 仿真保真度分层

### 7.1 三级仿真模型

```text
┌─────────────────────────────────────────────────────────────┐
│ L3 物理仿真（高保真）                                         │
│ 模拟传感器信号、网络抖动、硬件故障、电源波动                      │
│ 适用：压力测试、混沌测试、边界场景                               │
├─────────────────────────────────────────────────────────────┤
│ L2 状态仿真（中保真）                                         │
│ 模拟设备状态机（待机→开门→取货→关门→结算）                       │
│ 适用：业务流程测试、端到端验证                                   │
├─────────────────────────────────────────────────────────────┤
│ L1 协议仿真（低保真）                                         │
│ 模拟 MQTT/WebSocket 消息格式和基本交互                         │
│ 适用：接口联调、协议兼容性测试                                   │
└─────────────────────────────────────────────────────────────┘
```

### 7.2 各层能力对比

| 能力 | L1 协议仿真 | L2 状态仿真 | L3 物理仿真 |
|------|-----------|-----------|-----------|
| 消息格式正确性 | 支持 | 支持 | 支持 |
| 设备状态机 | 不支持 | 支持 | 支持 |
| 传感器数据模拟 | 不支持 | 部分 | 完整 |
| 网络异常模拟 | 不支持 | 部分 | 完整 |
| 硬件故障模拟 | 不支持 | 不支持 | 支持 |
| 支持设备规模 | 百万级 | 十万级 | 千级 |
| 资源消耗 | 低 | 中 | 高 |

## 八、AI 评测自动化流水线

### 8.1 评测流水线设计

```text
触发条件：
├── 模型版本更新
├── 测试数据集更新
├── 定时回归（每周）
└── 手动触发
    │
    ▼
评测准备
├── 拉取模型版本
├── 拉取数据集版本
├── 分配 GPU 资源
└── 初始化评测环境
    │
    ▼
执行评测
├── 批量推理（支持分布式）
├── 结果比对（vs Ground Truth）
├── 指标计算（准确率 / 召回率 / F1）
└── 性能统计（延迟 / 吞吐 / 显存）
    │
    ▼
结果分析
├── 多版本横向对比
├── 按维度拆分（SKU / 国家 / 光照 / 场景）
├── 失败 Case 归类
└── 回归检测（与上一版本对比）
    │
    ▼
输出报告
├── 评测报告（可视化）
├── 回归告警（如有退化）
├── 模型质量评分
└── 推荐发布 / 阻断发布
```

### 8.2 评测数据集管理

```text
数据集结构：
├── 基础集（Baseline）
│   ├── 标准光照商品图片 × 5000
│   └── 标准场景视频 × 1000
├── 挑战集（Challenge）
│   ├── 低光照 / 逆光 / 反光 × 2000
│   ├── 多商品重叠 × 500
│   └── 用户遮挡 × 500
├── 海外集（Regional）
│   ├── 各国特有商品 × 3000
│   └── 各国特殊场景 × 500
└── 回归集（Regression）
    └── 历史线上问题 Case × 1000

版本管理：
├── 数据集使用 Git LFS 或 DVC 管理
├── 每次变更记录变更原因
└── 数据集与模型版本绑定
```

## 十、存储分层设计

### 10.1 数据分层策略

```text
┌─────────────────────────────────────────────────────────┐
│ 热数据（最近 7 天）                                        │
│ 存储：ClickHouse / Elasticsearch                         │
│ 内容：最近测试结果、实时监控指标、在线设备状态                  │
│ 访问：毫秒级                                              │
├─────────────────────────────────────────────────────────┤
│ 温数据（7 天 ~ 90 天）                                     │
│ 存储：对象存储 + 索引层                                    │
│ 内容：历史测试报告、Trace 日志、缺陷快照                     │
│ 访问：秒级                                                │
├─────────────────────────────────────────────────────────┤
│ 冷数据（90 天以上）                                        │
│ 存储：对象存储（低频访问层）                                 │
│ 内容：视频回放、AI 原始推理结果、归档报告                    │
│ 访问：分钟级（需解冻）                                     │
└─────────────────────────────────────────────────────────┘
```

### 10.2 存储容量估算

| 数据类型 | 单条大小 | 日增量 | 存储层 | 90 天总量 |
|---------|---------|--------|--------|----------|
| 测试结果 | 5 KB | 10 万条 | 热→温 | ~45 GB |
| Trace 日志 | 2 KB | 100 万条 | 热→温 | ~180 GB |
| AI 推理结果 | 50 KB | 10 万条 | 热→温 | ~450 GB |
| 视频回放 | 50 MB | 1000 条 | 温→冷 | ~4.5 TB |
| 设备日志 | 1 KB | 1000 万条 | 热→温→冷 | ~900 GB |

## 十一、技术选型补充

### 11.1 前端技术栈

| 模块 | 推荐方案 | 理由 |
|------|---------|------|
| 框架 | React + TypeScript | 生态成熟，团队人才多 |
| DAG 编排 | React Flow / X6 | 可视化流程编排，支持自定义节点 |
| 数据可视化 | ECharts + Grafana 嵌入 | 复杂图表用 ECharts，监控面板复用 Grafana |
| 视频播放 | Video.js + 自研叠加层 | 支持 AI 识别结果标注叠加 |
| 实时通信 | WebSocket | 设备状态、任务进度实时推送 |

### 11.2 消息队列细化

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| IoT 指令下发 | RocketMQ | 支持延迟消息、优先级队列、事务消息 |
| 日志采集 | Kafka | 高吞吐、顺序写入、多消费者 |
| 任务调度 | Redis Streams | 低延迟、轻量级、支持消费者组 |
| 事件通知 | RabbitMQ | 灵活路由、支持多种模式 |

### 11.3 全文检索与分析

```text
数据流向：
设备日志 / IoT消息 / 测试日志
    │
    ▼
Kafka（缓冲）
    │
    ├──→ Elasticsearch（全文检索、Trace 查询）
    ├──→ ClickHouse（OLAP 分析、指标聚合）
    └──→ S3/OSS（冷归档）
```

## 十四、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 真实设备资源不足 | 无法覆盖硬件相关测试 | 虚拟设备优先 + 真机按需申请 |
| IoT 协议频繁变更 | 仿真引擎维护成本高 | 协议版本化 + 向后兼容设计 |
| AI 模型迭代快 | 评测流水线跟不上 | 自动触发 + 增量评测 |
| 海外网络不稳定 | 测试执行成功率下降 | 多 Region 部署 + 重试机制 |
| 多团队协作冲突 | 设备 / 环境抢占 | 资源预约 + 优先级队列 |
| 平台自身稳定性 | 影响所有测试活动 | 高可用部署 + 降级方案 |
